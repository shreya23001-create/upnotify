1. Executive Summary

This report documents the current state of monitor location checking in Upnotify, the changes shipped in this session, and what remains to achieve true geographically-distributed checking.

What shipped this session
Region configuration (7 global locations), region tagging on every check result, and a new Location column in the Check History UI. The region field was always in the database schema — it was simply never being populated. It now is.
Current limitation
Both the primary check and the confirmation check still execute from the same Vercel serverless region. The region field now correctly records where the check ran. Routing checks to physically separate locations requires additional infrastructure (separate deployments or external workers) — the config and DB are ready for it.

2. How Monitoring Worked Before

The check runner at app/api/cron/check-runner/route.ts implemented a two-confirmation pattern:

1
Phase 1 — Primary check (all monitors in parallel)
Dispatch all due monitors concurrently. Write result to check_results. Region: never set — always NULL.
2
Phase 2 — Handle UP monitors immediately
Monitors that came back UP get their status updated and next check scheduled right away. Resolved incidents trigger recovery alerts.
3
Phase 3 — Confirm DOWN monitors (after 5 s sleep)
Monitors flagged DOWN in Phase 1 are re-checked. If still DOWN → incident created + alerts dispatched. If now UP → flap counter incremented. Region: never set — always NULL.
Root cause of missing region data
The writeCheckResult() function accepted an optional region parameter since the schema was created, but neither call site in the check runner ever passed it. All historical records have region = NULL.

export function getCurrentRegion(): string {
  return process.env.VERCEL_REGION ?? 'iad1'
}

export function getRegionLabel(regionId: string | null | undefined): string {
  if (!regionId) return '—'
  const r = REGION_MAP.get(regionId)
  return r ? `${r.flag} ${r.label}` : regionId
}

5. Roadmap — True Multi-Region Checking

The following steps are needed to achieve checks from genuinely different physical locations.

Option A — Vercel Edge Config + Multiple Deployments (Recommended)

Deploy the check runner as a Vercel Edge Function in each target region. Vercel allows regions to be configured per function. Each deployment handles its own monitors and writes results with its own VERCEL_REGION.

Effort
Medium. Requires Vercel Pro or Enterprise for custom region pinning. No new infrastructure vendors.

Option B — External Workers (Fly.io / Railway)

Run lightweight check worker processes on Fly.io machines in each target region. Each worker polls a check_jobs queue, runs the check, and POSTs results back to the Upnotify API with its region ID.

Effort
High. New infrastructure, worker lifecycle management, auth between workers and API.

Option C — Ping/HTTP via Regional Probe APIs

For HTTP and Ping monitor types, delegate to third-party probe APIs (e.g. Updown.io probes, Freshping probes, or a custom edge network) and aggregate results. Lower infrastructure cost, less flexibility.

Effort
Low. Limited to monitor types the probe API supports.

6. Majority-Vote DOWN Detection (Future Logic)

Once checks run from multiple physical regions, the confirmation logic in check-runner/route.ts should be upgraded from "re-check from same location" to "check from N different locations, declare DOWN only if majority agree":

// Future Phase 3 — multi-region confirmation
const CONFIRMATION_REGIONS = ['iad1', 'lhr1', 'sin1']
const QUORUM = 2 // 2 of 3 must agree DOWN to create incident

const confirmations = await Promise.allSettled(
  CONFIRMATION_REGIONS.map(region => dispatchCheckerFromRegion(monitor, region))
)

const downCount = confirmations.filter(
  r => r.status === 'fulfilled' && r.value.status === 'down'
).length

if (downCount >= QUORUM) {
  // Create incident — confirmed from multiple locations
}
