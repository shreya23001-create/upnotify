Issues Found

TIER 1 — REVENUE LOSS
Credit application does not create Stripe invoice item — customers charged full price
Phase 2 of applyCreditsToStripeInvoice() (creating a negative Stripe invoice item) is commented out with a TODO. Credits are marked "applied" in DB but Stripe never receives the deduction. Every credit redemption results in a full-price charge.
✦ Fix: Implement the commented Phase 2 code. Call stripe.invoiceItems.create({ amount: -totalAppliedPence, currency: 'gbp', customer: stripeCustomerId }) before the invoice is finalized. Test with Stripe test mode.
lib/db/user-credits.ts · applyCreditsToStripeInvoice() · line 241
Razorpay annual upgrade credit never automatically processed
Annual upgrade credits are correctly calculated and stored in razorpay_annual_upgrade_log as 'pending', but require a manual admin to mark each as 'refunded'. No automatic refund, no customer notification, no SLA on processing.
✦ Fix: Integrate Razorpay's Refund API. After logging the credit, call razorpay.refunds.create({ payment_id, amount: creditAmountPaise }) and update the log with the refund ID and status. Notify the user by email.
app/api/webhooks/razorpay/route.ts · handleSubscriptionActivated()
TIER 2 — DATA INTEGRITY
Invoice amount_gbp column stores INR paise for Razorpay invoices
The invoices table has an amount_gbp column used for both GBP pence (Stripe) and INR paise (Razorpay). Revenue dashboard mixes currencies, making totals wrong.
✦ Fix: Add a separate amount_inr column. Migrate Razorpay invoice records. Update revenue aggregation queries to sum each currency column separately.
app/api/webhooks/razorpay/route.ts · handleSubscriptionCharged() · line 297
Razorpay refund summary uses credit_amount as fallback — partial refunds counted incorrectly
refunded_amount_inr ?? credit_amount_inr means records with partial refunds (refunded less than credited) show the full credit amount in the total, inflating the "total refunded" figure.
✦ Fix: Only include records in the refunded total where refunded_amount_inr IS NOT NULL. Show credit_amount vs refunded_amount separately in the admin UI.
app/api/admin/revenue/razorpay-upgrades/route.ts · line 110
Duplicate getPlanBySlug() in two files
Same function exists in both lib/db/subscriptions.ts and lib/db/plans.ts. Future schema changes must be applied in two places.
✦ Fix: Keep canonical version in lib/db/plans.ts. Import and re-export from subscriptions.ts if needed for backwards compatibility.
TIER 3 — SECURITY / OPERATIONAL
Mock mode not blocked in production — payment bypass risk
If deployed with RAZORPAY_KEY_ID=rzp_test_placeholder, all Razorpay checkout calls silently succeed with a mock subscription ID. Webhooks reject these IDs, but the user receives a "checkout success" response without paying.
✦ Fix: Detect production environment (process.env.NODE_ENV === 'production'). In production, if key is placeholder, return 500 error instead of mock response. Never silently succeed a payment in production.
app/api/v1/billing/razorpay/checkout/route.ts · line 70
Razorpay webhook signature not enforced — accepts unverified payloads in dev/staging
In non-production environments, signature mismatch logs a warning but processing continues. Allows crafted webhook payloads to manipulate subscription state in staging environments.
✦ Fix: Always enforce signature validation. For local dev, use Razorpay's test webhook tool or forward real webhooks via ngrok with the real secret. Never process unverified webhooks.
app/api/webhooks/razorpay/route.ts · line 394
TIER 4 — FUNCTIONAL GAPS
AI report limit never enforced — unlimited generation regardless of plan
checkAiReportLimit() always returns { allowed: true } with a TODO comment. All users on all plans can generate unlimited AI reports.
✦ Fix: Add a COUNT(*) query to reports table for the current calendar month (generated_at >= start_of_month). Compare against plan.aiReportLimit. Reject if exceeded.
lib/utils/plan-limits.ts · line 215
Invisible plans can be purchased via checkout API
Checkout only validates plan existence, not is_visible=true. Hidden/retired plans can be purchased by guessing the plan slug.
✦ Fix: Add .eq('is_visible', true) filter to the plan lookup in both Stripe and Razorpay checkout routes.
Trial subscription silently skips if any prior subscription exists (including cancelled)
createTrialSubscription() skips if count > 0 without filtering by status. A user who was on free and cancelled cannot start a trial.
✦ Fix: Add .in('status', ['active', 'trialing', 'paused']) filter. Only skip trial if there is a currently active/paused subscription, not a historical cancelled one.
lib/db/subscriptions.ts · createTrialSubscription()
Deactivated team members counted against seat limit
checkTeamMemberLimit() does not filter by is_active. If a user is deactivated, they still occupy a seat, preventing adding new members.
✦ Fix: Add .eq('is_active', true) to the user count query in checkTeamMemberLimit().
lib/utils/plan-limits.ts · checkTeamMemberLimit()
TIER 5 — PERFORMANCE / MINOR
No subscription state change audit trail
Subscriptions have created_at only. Cannot determine when a subscription went from active → past_due → cancelled or who initiated a cancellation.
✦ Fix: Add updated_at (auto-updated trigger) and a subscription_events log table recording each status transition with timestamp and triggering webhook/action.
Revenue dashboard stores only first user per org in email map
usersByOrgId map is built with map[user.org_id] = user — overwrites on multiple users. Multi-seat orgs show the wrong contact email in the revenue table.
✦ Fix: Map orgId → user[] (array). Display primary owner (user.role === 'owner') email in the UI, with a "View all" link.
app/api/admin/revenue/route.ts · line 173

Suggestions & Improvements

Immediate — Revenue Protection

Complete Phase 2 of credit application — this is a silent revenue leak affecting every credit user
Implement automatic Razorpay refund API call after annual upgrade credit calculation
Add is_visible=true filter to both checkout routes to prevent retired plan purchases
Block mock mode in production via NODE_ENV check — prevents accidental payment bypass on deploy

Short-Term — Data Quality

Add separate amount_inr column to invoices table — stop mixing currencies in a GBP-named column
Implement AI report monthly count limit — the TODO has been open; implement the COUNT(*) query
Add subscription_events audit table — every status transition logged with timestamp
Fix trial subscription logic to filter by active status, not just existence

Architecture

Consolidate getPlanBySlug() to one file (lib/db/plans.ts) — prevents future divergence
Add Razorpay webhook enforcement in all environments — use ngrok or Razorpay test tool for local dev
Add revenue CSV export endpoint for accounting — query invoices, format as CSV, stream response
Consider Razorpay credit note flow for monthly-to-annual downgrades — currently no code path handles this
