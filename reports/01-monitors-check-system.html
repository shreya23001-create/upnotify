Working Flow

Phase 1 — Primary Check (All Monitors in Parallel)
1
getDueMonitors() — fetches up to 100 monitors where next_check_at ≤ now and is_paused = false
↓
2
Maintenance filter — parallel calls to isMonitorInMaintenance() for each monitor. Maintenance monitors skip checks and update next_check_at only.
↓
3
dispatchChecker(monitor) — routes to one of 23 checker functions based on monitor.type. Each checker runs the actual check (HTTP, DNS, SSL, etc.).
↓
4
writeCheckResult() — saves result with status, response_time_ms, status_code, error_message, metadata, and region (from VERCEL_REGION env var).
↓
5
patchMonitorConfig() — persists baseline values for change-detection monitors (IP, DNS, robots.txt hash, nameservers, WHOIS snapshot).
Phase 2 — Handle UP Monitors Immediately
1
UP monitors (status ≠ 'down') are handled immediately — no wait.
↓
2
Was previously DOWN? → resolveIncident(monitorId) sets status=resolved, records resolved_at and duration_seconds. Then dispatchRecoveryAlerts() fires to all enabled channels.
↓
3
updateMonitorStatus() — sets new status, last_checked_at=now, next_check_at = scheduleBase + check_interval_seconds.
Phase 3 — Confirm DOWN Monitors (Anti-Flap, After 5-Second Sleep)
1
sleep(5000ms) — waits before re-checking to avoid false positives from transient blips.
↓
2
dispatchChecker(monitor) again — confirmation check from same region.
↓
3
writeCheckResult() — saves with metadata.isConfirmationCheck = true and region.
↓
4a
Still DOWN → getOpenIncidentForMonitor(). If no open incident → createIncident() → dispatchAlerts() to all enabled channels.
4b
Now UP → incrementFlapCount(monitor.id) — logged as transient flap, no incident created.
Alert Dispatch Flow
1
Fetch enabled alert channels for org, filtered by monitor severity.
↓
2
getAlertCopy() — resolves 27 placeholders ({{monitorName}}, {{target}}, {{downDuration}}, {{daysUntilExpiry}}, etc.) into subject, headline, detail, shortText, voiceScript.
↓
3
Parallel dispatch to: Email, Slack (Block Kit), Teams (MessageCard), Webhook (HMAC-signed JSON), Telegram (text), In-App (user_messages row for org admin).
↓
4
Each dispatch recorded in alerts table with status ('sent' or 'failed') + error_message if failed.

Issues Found

CRITICAL — Feature Broken
Heartbeat monitor uses wrong timestamp — always reports UP
The heartbeat checker reads monitor.last_checked_at to determine if a ping was received within the expected interval. But last_checked_at is updated by the cron runner after every status check — not by the user's actual heartbeat ping. The field is always recent, so all heartbeat monitors permanently report "up" even if the underlying job has stopped running.
✦ Fix: Add a separate last_heartbeat_at column to monitors. Create a dedicated POST endpoint (e.g. /api/v1/heartbeat/{monitorId}) that updates this field when the user's job pings it. The checker should compare last_heartbeat_at (not last_checked_at) against expectedIntervalSeconds.
lib/checkers/heartbeat.ts
HIGH SEVERITY
No alert rate-limiting — flapping monitor can send 288 alerts/day
If a monitor flaps between down and up every 5-minute cycle, the alert dispatcher fires a down alert + recovery alert on every cycle. With no throttle, this is up to 288 emails/Slack messages per day per monitor.
✦ Fix: Add a last_alert_sent_at column to the monitors or alerts table. In dispatchAlerts(), skip dispatch if the last alert was sent less than 10 minutes ago (configurable per org). Log suppressed alerts.
lib/services/alert-dispatcher.ts
No retry queue for failed alert deliveries
When a webhook, email, or Slack alert fails, it is logged as 'failed' in the alerts table and never retried. Users miss critical down notifications.
✦ Fix: Add a retry_after column to the alerts table. A separate cron (or the same runner) picks up failed alerts with exponential backoff (1m → 5m → 15m, max 3 retries).
lib/services/alert-dispatcher.ts
100-monitor hard limit per cron run silently skips monitors
getDueMonitors() is capped at 100. Organisations with >100 monitors silently skip some every run. With 1-minute intervals, some monitors may never check.
✦ Fix: Increase limit or implement a round-robin queue. Use a priority field (overdue monitors get highest priority). Or split into multiple cron invocations with offset.
lib/db/monitors.ts · getDueMonitors()
Maintenance window queried 100× per cron run — no caching
For every monitor, isMonitorInMaintenance() makes a separate DB call. On a 100-monitor run this is 100 queries to the same table for the same time window.
✦ Fix: Fetch all active maintenance windows once at the start of the runner. Pass them as a Map into the maintenance check function. Reduces 100 queries to 1.
lib/db/maintenance-windows.ts
MEDIUM SEVERITY
Race condition: config and status updates are two separate DB calls
In the check runner, patchMonitorConfig() and updateMonitorStatus() are separate calls. If the runner crashes between them, the baseline is not persisted but the status is marked as checked — next run compares against stale baseline.
✦ Fix: Combine into a single PATCH call that updates both config and status fields atomically. Or wrap in a Supabase RPC transaction.
app/api/cron/check-runner/route.ts
Flap count increments forever — never resets or decays
incrementFlapCount() adds 1 each time a flap is detected but there is no reset condition, TTL, or windowed decay. Becomes a permanent ever-growing counter of no operational value.
✦ Fix: Reset flap_count to 0 when the monitor has been stable for a configurable window (e.g. 24 hours without a flap). Or cap at 255 and reset.
lib/db/monitors.ts · incrementFlapCount()
DNS checkers have no explicit timeout — can hang indefinitely
dns.resolveMx(), dns.resolveTxt() and others rely on OS-level DNS timeouts. If a DNS server is unresponsive, the check hangs until OS times out (can be 30+ seconds), blocking the runner.
✦ Fix: Wrap all dns.resolve*() calls in Promise.race([dnsPromise, timeout(8000)]). Return { status: 'down', errorMessage: 'DNS timeout' } on timeout.
lib/checkers/dns.ts, mx-health.ts, spf-dmarc.ts
New monitors show 100% uptime before first check (misleading)
getMonitorUptimePercentage() returns 100 when no check results exist. Status pages and dashboard show "100% uptime" for a brand-new monitor with zero data.
✦ Fix: Return null when data.length === 0. Render "No data yet" in the UI instead of 100%. File: lib/db/check-results.ts:184.
lib/db/check-results.ts
LOW / DESIGN NOTES
Alert copy placeholders not validated before dispatch
If incident metadata is missing a field referenced in the alert template (e.g. {{responseTime}} when metadata.responseTimeMs is undefined), the literal placeholder string is sent in the alert email.
✦ Fix: In getAlertCopy(), validate all required placeholders exist for the monitor type. Fall back to a generic value (e.g. "N/A") rather than leaving the raw token.
Competitor checker bypasses dispatchChecker() — called directly from cron
The hourly competitor cron calls checkCompetitorDomain() directly instead of routing through dispatchChecker() like every other monitor type. Inconsistent architecture.
✦ Fix: Use the existing check() wrapper adapter in competitor.ts via dispatchChecker() for consistency. Makes future changes (region tracking, error handling) apply automatically.
Response-time degraded threshold hardcoded at 70% — not user-configurable
All response-time monitors use degradedMs = thresholdMs × 0.7. Some sites may want a different ratio.
✦ Fix: Add optional degradedPercent (default 70) to CheckerConfig. Expose in the monitor edit form.
No bulk monitor operations (pause, delete, reconfigure)
All monitor actions are individual queries. Users cannot bulk-pause all monitors for a domain or bulk-update check intervals.
✦ Fix: Add batch API endpoints accepting an array of monitor IDs. Add checkbox multi-select to the monitors list UI.
Legacy keyword config (string) not migrated to array format
Old monitors use config.keyword (string) + config.shouldExist (boolean). New monitors use positiveKeywords[] + negativeKeywords[]. Both work but there is no migration script.
✦ Fix: Write a one-time migration that converts all config.keyword + shouldExist fields to the new array format. Remove legacy handling from checker after migration.

Suggestions & Improvements

Immediate Wins (1–3 days each)

Implement the heartbeat POST endpoint (/api/v1/heartbeat/{id}) — this is a complete feature break, not a minor bug
Wire alert rate-limiting using existing last_checked_at pattern — protect users from notification spam
Move maintenance window fetch to one call at runner start — free performance win, no schema change needed
Return null from getMonitorUptimePercentage() when no data — prevents misleading 100% display

Short-Term (1–2 weeks)

Add alert retry queue — failed webhook/email alerts should be retried with backoff (1m → 5m → 15m, max 3 attempts)
Implement DNS checker timeouts via Promise.race() — prevents hanging checks from blocking runner
Add flap count decay — reset after 24h stable period, or use a windowed moving average
Bulk monitor operations — users with many monitors need multi-select pause/delete/reconfigure

Architecture Suggestions

Increase or paginate monitor limit — use a cursor-based approach (WHERE id > last_cursor) for fair distribution across large orgs
True multi-region checks — deploy check runner to 2 Vercel regions; confirmation check routes to a different region for genuine geographic diversity
Majority-vote incident creation — when multi-region is live, only create incident if ≥2 of 3 regions report DOWN
Atomic config+status update — use a Supabase RPC to merge patchMonitorConfig and updateMonitorStatus into one call
