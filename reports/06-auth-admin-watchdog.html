Issues Found

Critical — Security Impersonation Cookie Is Unsigned — Session Spoofing Risk

The impersonation_token cookie that tracks active admin impersonation sessions is stored without a cryptographic signature. Any attacker who can write an arbitrary cookie value (via XSS or browser dev tools on a shared machine) can forge an impersonation session and access another user’s account data. This bypasses all authentication. The cookie should be signed with a server secret before being stored on the client.

Recommended Fix

Sign the impersonation token using HMAC-SHA256 with a server-side secret (IMPERSONATION_SECRET from getServerConfig()). Verify the signature server-side on every request that reads the cookie. Alternatively, store the impersonation state entirely server-side in a short-lived DB record keyed by a random session ID, with no sensitive data in the cookie at all.

📄 app/api/admin/impersonate/route.ts · middleware.ts · lib/utils/cookies.ts
Critical — Security Admin Panel Pages Lack Server-Side Permission Checks

Admin panel routes under /admin/* rely on a client-side redirect in the layout component to enforce access. If a user navigates directly to an admin API route (e.g., /api/admin/users, /api/admin/impersonate) without going through the layout, there is no server-side is_admin check on the API routes themselves. Middleware only checks authentication (session exists) but not the admin role. This means any authenticated user can call admin API endpoints directly.

Recommended Fix

Add an explicit is_admin check at the top of every /api/admin/* route handler before any logic executes. Create a requireAdmin() helper in lib/auth/guards.ts that reads the current session, looks up users.is_admin, and returns a 403 if false. Call requireAdmin() as the first line of every admin route. Do not rely on layout-level redirects for security.

📄 app/api/admin/*/route.ts · lib/auth/guards.ts
Critical — Security Auth Rate Limiting Not Wired to Login Endpoint

The in-memory rate limiter exists in lib/utils/rate-limiter.ts and is used on some monitor API routes, but it is not applied to the /api/auth/login or /api/auth/verify-otp endpoints. An attacker can send unlimited login attempts or OTP verification requests, enabling brute-force attacks against OTP codes (6-digit = 1,000,000 combinations, easily brute-forced at high request rates). Supabase has its own rate limiting but this should not be the only defense.

Recommended Fix

Apply the existing rate limiter to /api/auth/* routes: max 10 login attempts per IP per 15 minutes. On 10th failure, add a 15-minute lockout. Log excessive attempts to watchdog_events for admin visibility. Also enable Supabase’s built-in email OTP rate limiting in the Supabase dashboard (Auth > Rate Limits) as a second layer.

📄 app/api/auth/login/route.ts · app/api/auth/verify-otp/route.ts · lib/utils/rate-limiter.ts
High Impersonation Actions Not Consistently Attributed in Audit Log

When an admin is impersonating a user and performs actions (editing a monitor, changing a plan), those actions should be recorded with both the target user_id and the impersonator_id. Currently, some write operations during impersonation use the target user’s session directly without recording the impersonator. This means post-incident investigations cannot determine whether a change was made by the user or an admin acting on their behalf.

Recommended Fix

Add an impersonator_id column to all audit-relevant tables (monitor_events, billing_events, watchdog_events). When an impersonation session is active, the API middleware should inject impersonator_id into all write operations. Create a DB function or trigger that automatically populates this field when the impersonation cookie is present.

📄 lib/auth/session.ts · lib/db/audit.ts · middleware.ts
High Team Member Role Checks Not Enforced at DB Layer for All Resources

RLS policies enforce team membership at the database layer, but the role within the team (Owner vs Editor vs Viewer) is only checked in application code, not in RLS policies. An Editor who knows the API endpoint for billing changes could craft a direct API call that the DB would not reject, relying entirely on application-level checks that may have gaps.

Recommended Fix

Extend RLS policies to check team role for sensitive operations: billing_events (INSERT/UPDATE restricted to role IN ('owner')), monitor_deletes (restricted to role IN ('owner', 'editor')). Store the role in team_members table and reference it in RLS policy conditions. This makes role enforcement tamper-proof at the DB layer.

📄 supabase/migrations/ · lib/db/team-members.ts
Medium Watchdog Thresholds Are Hardcoded — Cannot Be Tuned Without Deploy

The watchdog anomaly detection uses hardcoded thresholds (10 failed logins/hour, 5 monitor deletes/hour, 3 plan changes/day). These are arbitrary values that cannot be adjusted without a code change and deployment. As Uptrue scales, these thresholds will generate too many false positives (for power users) or miss genuine attacks.

Recommended Fix

Move thresholds to a watchdog_config table managed via the admin panel. Allow per-metric configuration with name, threshold, window_minutes, and severity. Add a test mode that simulates alerts without sending emails. This enables real-time tuning of sensitivity without code deploys.

📄 app/api/cron/watchdog/route.ts · lib/services/watchdog.ts
Medium Watchdog Alerts Only Go to Email — No Slack or In-App Notification

Watchdog anomaly alerts are sent only to a hardcoded admin email address. There is no Slack webhook, no in-app admin notification, and no way to route different alert types to different channels. If the admin email is unmonitored during off-hours, critical security events go unnoticed.

Recommended Fix

Extend the watchdog alert system to support multiple channels: email (existing), Slack webhook (configurable in admin panel), and in-app notification badge visible on the /admin dashboard. For Critical severity events, send to all channels simultaneously. Use the same alert-channel abstraction already used in the monitor alert system.

📄 lib/services/watchdog.ts · lib/services/alert-dispatcher.ts
Medium Session Tokens Not Invalidated on Password or Email Change

When a user changes their email address or auth method (e.g., switches from magic link to Google OAuth), existing sessions from other browsers or devices remain valid. An attacker who has already captured a session token can continue to use it even after the user has updated their credentials. Industry standard is to invalidate all sessions on credential change.

Recommended Fix

On email or auth method change, call Supabase’s admin.auth.signOut(userId, 'others') to invalidate all other active sessions for that user. Show the user a confirmation: “All other sessions have been signed out.” Log this event to watchdog_events as a security-relevant action.

📄 app/api/auth/update-email/route.ts · lib/auth/session.ts
Low Admin User Search Returns Full User Objects Including Sensitive Fields

The /api/admin/users search endpoint returns full user records including encrypted_api_keys, billing_customer_id, and other sensitive fields that are not needed for the search result display. This creates unnecessary data exposure in network traffic and browser DevTools.

Recommended Fix

Create a dedicated AdminUserSummary type that selects only the fields needed for the admin UI: id, email, created_at, plan, is_active, last_login. Use this type in the search query SELECT clause. Never return encrypted API keys or payment tokens to the frontend, even in admin context.

📄 app/api/admin/users/route.ts · lib/db/users.ts
Low Team Invite Links Do Not Expire on First Use

Team invitation links expire after 48 hours but are not invalidated after first use. If an invitation email is forwarded or the link is shared accidentally, a second person can use the same link to join the organisation under the invited email address. The invitee would then have two accounts joined to the same team slot.

Recommended Fix

Mark invite tokens as used immediately upon the first successful acceptance (UPDATE team_invites SET used_at = NOW() WHERE token = ?). On acceptance, check used_at IS NULL before proceeding. Show a clear error for already-used tokens. This is a one-line DB update in the accept handler.

📄 app/api/team/accept-invite/route.ts · lib/db/team-invites.ts

Suggestions & Improvements

Immediate (This Sprint) — Security

  • Sign impersonation cookie with HMAC-SHA256 using server secret
  • Add requireAdmin() guard to all /api/admin/* route handlers
  • Wire existing rate limiter to /api/auth/login and /api/auth/verify-otp
  • Invalidate all sessions on email or auth method change
  • Mark invite tokens as used on first acceptance

Short-Term (1–2 Sprints)

  • Extend RLS policies to enforce team role (not just membership) for billing/delete operations
  • Add impersonator_id to all audit-relevant write operations
  • Add Slack webhook + in-app notification to watchdog alert dispatch
  • Move watchdog thresholds to admin-configurable DB table
  • Restrict admin user search to AdminUserSummary fields only

Architecture

  • Centralised audit log table with actor_id, impersonator_id, action, resource_type, resource_id, metadata — single source of truth for all system events
  • Role-based access control (RBAC) library: centralise all permission checks in lib/auth/rbac.ts to avoid scattered role checks across route handlers
  • Admin panel real-time activity feed using Supabase Realtime for live watchdog events
  • MFA (TOTP) support for admin accounts and optionally for all users as a plan feature
  • Session management page for users: see all active sessions, sign out individual devices
