### TC-144-01: Unregistered email does not reveal account existence (account enumeration)

**Given** I am logged out on https://dev.uptrue.io/login
**When** I enter a never-registered email (e.g. `nobody-zzz999@example.com`) and click **Send Magic Link →**
**Then** I see the same **"Check your email"** confirmation screen shown for a real account
  **AND** no error such as "no account found" / "email not registered" appears
  **AND** no email arrives (the address is unregistered)
  **AND** the response timing/copy is indistinguishable from a registered email.

**Notes:** Server collapses every non-rate-limit Supabase OTP error to a neutral response (`lib/auth/actions.ts` → `signInWithEmail`). Only rate-limiting returns a distinct "too many attempts" message. Covered by `tests/unit/auth/*`.

### TC-149-01: Free plan blocked from 4th monitor via REST API (server-side 403)

**Given** a Free-plan org that already has 3 monitors, and a valid API key
**When** I `POST https://dev.uptrue.io/api/v1/monitors` directly (curl/Postman) with a valid body and `Authorization: Bearer <key>`
**Then** the response is **403 Forbidden** — not 200, not just a UI block
  **AND** the body is `"API access is not available on your current plan. Upgrade to use the REST API."` (Free has no API access at all)
  **AND** no monitor is created.

```bash
curl -i -X POST https://dev.uptrue.io/api/v1/monitors \
  -H "Authorization: Bearer <FREE_PLAN_API_KEY>" \
  -H "Content-Type: application/json" \
  -d '{"name":"t","type":"http","target":"https://example.com"}'
```

**Notes:** Two independent 403 gates exist — (1) no API access on plan, (2) monitor count over limit. For a plan that DOES have API access but is over its monitor cap, expect 403 `"Monitor limit reached (x/y)..."`. Covered by `tests/unit/plan-limits.test.ts`.

### TC-150-01: Create a robots.txt monitor

**Given** I am logged in as a Builder or Scale plan user
**When** I go to **New Monitor**, select **robots.txt Change**, enter a domain (e.g. `example.com`), and Save
**Then** the monitor is created and appears in the monitors list with type "robots.txt Change"
  **AND** the monitor page loads without a 404.

### TC-150-02: Googlebot block raises a P1 alert

**Given** a robots.txt monitor exists for a domain I control, with at least one baseline check recorded
**When** I change that site's `/robots.txt` to `User-agent: Googlebot` + `Disallow: /` (or `User-agent: *` + `Disallow: /`) and wait for the next check + 30s confirmation
**Then** an incident opens with severity **P1** (even if the monitor was created at the default P2)
  **AND** the alert copy states robots.txt is blocking Googlebot (SEO critical).

**Notes:** This is the fix landed 2026-06-30 — `severityOverride: 'P1'` in `lib/checkers/robots-txt.ts`, honoured by the check-runner. Covered by `tests/unit/checkers/robots-txt.test.ts` ("escalates severity to P1 when Googlebot is blocked").

### TC-150-03: Any change vs baseline is detected

**Given** a robots.txt monitor with a recorded baseline hash
**When** the target's robots.txt content changes (any edit) without blocking Googlebot
**Then** the check result is flagged as **changed / degraded** with message "robots.txt content has changed".

**Notes:** The step "modify robots.txt to block Googlebot" in the original ticket is a manual action on the **monitored target site** — it is NOT a control inside the Uptrue UI. Don't look for a button in Uptrue to edit robots.txt.

### TC-166-02: Footer "Status" link resolves

**Given** I am a logged-out visitor on https://dev.uptrue.io/
**When** I click the footer **Status** link
**Then** `/status` loads the status page — not a 404, not redirected to /login.

**Notes:** Root cause was the **DB-seeded footer** (migration 00090) linking API Docs to `/docs` (no such route → 404); the CMS row overrides the correct `/api-docs` code default. **Fix requires applying migration `00114_fix_footer_api_docs_href.sql` to the dev DB** — a code-only redeploy will NOT fix it. `/api-docs` and `/status` are both in `isPublicRoute`, and unknown routes render the custom 404 instead of bouncing to /login. Covered by `tests/unit/auth/helpers.test.ts` ("returns true for /api-docs and /status footer links").
